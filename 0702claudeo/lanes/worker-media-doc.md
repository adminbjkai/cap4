# Worker / Media-Server / Doc-Pipeline Audit

## 1. Summary — Grade: B+

Job-queue semantics (claim/heartbeat/ack/snooze/fail/reclaim) are unusually rigorous for a single-tenant side project — lease tokens, `SKIP LOCKED`, exponential backoff, a snooze-without-consuming-attempt primitive, and a watchdog for lost async webhooks. The doc pipeline's cost/safety engineering (cache-by-hash, dual call budgets, schema validation, retry-with-correction, screenshot-budget dedup) is genuinely well thought through. Weaknesses cluster around: zero automated test coverage for `media-server` (the actual ffmpeg pipeline), a host doc-worker that hardcodes container IPs at startup with no reconnect story, and a couple of narrow correctness edges in job-lease handling and model-call budget accounting.

## 2. Impressive strengths

- **Job queue design** — `apps/worker/src/index.ts:128-268`: single-statement `UPDATE...FOR UPDATE SKIP LOCKED` claim, lease-token-scoped ack/fail/snooze (prevents a reclaimed job from being double-acked by its original owner), and `snooze()` (`:216`) that releases a job without burning a retry attempt — used to defer `transcribe_video` while `process_video` is running (`:657`) instead of racing ffmpeg for CPU/bandwidth. This is a subtle, correct solution to a real resource-contention problem.
- **Async transcode handoff + watchdog** — `apps/worker/src/index.ts:388-410`: since `/process` replies 202 and media-server finishes out-of-band via webhooks, a crashed media-server would strand a video forever; the hourly maintenance query only fails videos with no active `process_video` job left, avoiding false positives against genuinely-slow transcodes.
- **Doc model-call economics** — `apps/worker/src/doc/model-client.ts:92-104` (cache-first) + `:173-181` (per-job and per-day budgets) + `apps/worker/src/doc/stage-c.ts:61-72` (cache key = sha256 of transcript+manifest+prompt version+model). One strong-model call per recording, capped at 16 images (`stage-c.ts:9`), with a corrective one-shot retry only when Stage D actually finds a hallucinated frame ref (`generate-doc.ts:159-169`) rather than blindly retrying every call.
- **Screenshot-spam guard** — `apps/worker/src/doc/stage-d.ts:57-106`: deterministic post-processing caps images per doc (6) and per frame (2), dedupes identical frame+crop pairs, and widens slivers rather than silently dropping them — every removal is logged into `confidence_notes` instead of failing silently.
- **No shell injection surface** — every ffmpeg/ffprobe/`claude` invocation across worker and media-server uses `spawn(bin, argsArray)` (`exec.ts:23`, `media-server/src/index.ts:60`), never a shell string; the one dynamic filter value (`FRAME_MAX_WIDTH` in `scale=min(1920\,iw):-2`) is a hardcoded constant, not user input.
- **Streaming, not buffering** — raw uploads and transcode inputs are always downloaded to a temp file and piped (`lib/s3.ts:38-50`, `media-server/src/index.ts:107-123`) rather than loaded into memory; per-attempt work dirs (`media-server/src/index.ts:290`) so a retried transcode can't delete a still-running sibling's files.

## 3. Issues, ranked by severity

**High — media-server has zero test coverage.** `apps/media-server/src/index.ts` is the only source file in that app; no `*.test.ts` exists, and `package.json:8` runs `vitest run --passWithNoTests`, so CI green-lights this silently. The remux-vs-transcode decision (`canRemux`, `:189-194`), the concurrent ffmpeg+thumbnail race, retry/backoff logic (`:268-285`), and webhook signing (`:207-242`) are all unverified by any automated test — only worker-side integration tests touch it indirectly. **Fix:** at minimum unit-test `canRemux`/`probeVideo` parsing and the webhook HMAC construction; a fixture-video integration test mirroring `pipeline.integration.test.ts` would catch regressions in the actual ffmpeg args.

**Medium — host doc-worker resolves container IPs once at process start, never reconnects.** `scripts/doc-worker.sh:26-31` bakes `PG_IP`/`MINIO_IP` into `DATABASE_URL`/`S3_ENDPOINT` env vars at launch. If `cap4-postgres-1` or `cap4-minio-1` is ever recreated (a `docker compose up -d --no-deps` on those services, or a host reboot that reorders container creation) while the doc-worker keeps running, every subsequent DB/S3 call fails until someone manually restarts the doc-worker — there's no retry-with-fresh-DNS. `waitForDatabaseReady()` (`index.ts:113-126`) only runs at startup, so mid-life IP drift isn't caught. Consistent with the `doc-worker-host-process` memory's documented "died, needed restart" incidents. **Fix:** re-resolve container IPs periodically or route the doc-worker through docker network DNS names.

**Medium — non-zero CLI exit and spawn errors are not retried within `generateStructured`, only via the outer job retry (and still count against the budget).** `model-client.ts:113-168`: the try/catch that drives the "retry once" logic wraps only JSON parsing (`:146-167`); if `this.opts.runner(...)` itself throws (ENOENT — `claude` missing) or the CLI exits non-zero (`:142-144`, e.g. logged-out subscription), the error propagates immediately, skipping the in-process retry. Recovery then depends on the outer job-queue backoff (up to `max_attempts`), and each attempt still calls `store.recordCall()` (`:117`) *before* the spawn even happens — so a broken environment (CLI missing/logged out) burns real entries against `DOC_MAX_MODEL_CALLS_PER_DAY` (default 60) without ever completing a doc, and can exhaust the daily budget purely on failures. **Fix:** distinguish "environment error" (ENOENT, auth failure) from "malformed output" and don't count environment errors against the daily call cap; surface a clearer "claude CLI unavailable" error class.

**Low — heartbeat loss doesn't interrupt the running job.** `index.ts:290-325`: `startHeartbeatLoop` only logs `job.heartbeat.lost` when the lease renewal fails; it never aborts the in-flight handler or kills a spawned child process. If a job's lease actually expires (DB blip during a long `claude -p` call exceeding `WORKER_LEASE_SECONDS`=60s default, three missed 15s heartbeats), `RECLAIM_SQL` (`:243-268`) will requeue the job for a different claim while the original invocation keeps running to completion, then fails its own `ack`/`fail` (both lease-token-scoped, so both no-op) — meaning the job could theoretically be processed twice concurrently, double-spending a model call. Low probability given the 60s/15s ratio and single-worker-per-job-type topology today, but no active mitigation.

**Low — SIGKILL only kills the immediate `claude` child, not a process tree.** `exec.ts:31-34`: `child.kill("SIGKILL")` on timeout. The test at `model-client.test.ts:160-169` explicitly notes "a grandchild would hold the stdio pipes open past the kill" — headless Claude Code may spawn subprocesses, and the current implementation would leak them past `DOC_MODEL_TIMEOUT_MS` (default 300s) if the real binary forks. **Fix (if confirmed):** spawn with `detached: true` and kill the process group (`process.kill(-child.pid, "SIGKILL")`).

**Low — duplicate maintenance work across worker instances.** `index.ts:1311-1315`: every worker process (both the container worker and the host doc-worker) runs `runMaintenance()` hourly, including the `process_video` watchdog UPDATE that's irrelevant to a doc-only worker. Harmless but wasted DB round-trips and a documented source of log noise ("column created_at does not exist" — worth root-causing rather than treating as permanently harmless). *(Cross-reference: the runtime lane confirmed this IS a real bug — see `lanes/runtime-health.md`, HIGH finding.)*

## 4. Design critiques

- **Frame extraction over-generates relative to what the model ever sees.** Up to 40 frames are detected, deduped, and uploaded to S3 (`generate-doc.ts:134-144`), but `thinFrames` (`stage-c.ts:11-18`) caps the model's view at 16 evenly-sampled frames — so on a scene-dense recording, up to 24 extracted/uploaded frames are structurally unselectable by the model. Not wrong, just wasted ffmpeg/S3 work; could thin before the S3 upload loop, or extract lazily only for the thinned set.
- **`isFatalError`/`.fatal` convention is informal.** Fatal-marking is done ad hoc per call site (`generate-doc.ts:249-261`) by mutating an `Error` with a bag property rather than a typed error class (contrast with `DocCallBudgetError`, which *is* a proper class). Easy to forget to set `.fatal` on a new terminal-failure case and get silent unnecessary retries.
- **`AnthropicApiDocModelClient` stub exists but has no config surface preventing accidental selection** beyond `DOC_MODEL_BACKEND` env value — fine today per the "subscription-only" policy, but worth a startup assertion (not just a runtime throw on first call) so a misconfigured `.env` fails fast instead of after a job is already claimed.

## 5. Test coverage assessment

Worker doc-pipeline tests are strong and well-targeted: `model-client.test.ts` (13 cases) exercises cache hit/miss, retry-on-malformed-JSON, schema-invalid failure, non-zero exit, both budget types, and an actual timeout-kill using a real spawned process — good use of real subprocess behavior instead of over-mocking. `pipeline.integration.test.ts` runs the full Stage A→D pipeline against a real ffmpeg-generated fixture video with only the model layer mocked, verifying the hallucinated-frame-ref retry path and crop/upload correctness end-to-end — genuinely valuable regression coverage. `stage-a`/`stage-c`/`stage-d` unit tests (7/7/11) cover scene parsing, capture-time selection, dedup logic, and markdown rendering. The opt-in `live-smoke.test.ts` (skipped unless `DOC_LIVE_SMOKE=1`) is a sensible pattern for validating the real CLI without burning credits in CI. The gap is entirely on the **media-server side — zero tests**, and the worker's own `providers/deepgram.test.ts`/`groq.test.ts` are thin (2 tests each) relative to their role as the two paid external API integrations.
